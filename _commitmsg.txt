fix: 能力对齐 ZCode 原生 —— 恢复采样参数透传、修并发限流、找回能力准则

三个独立的「DSH 里不如 ZCode 聪明」根因，逐项实测定位并修复。

## ① 采样参数全丢（能力差异的主因）

/diagnostics/direct 回显的 sent.bodyFields 只有四个：

    ["model","max_tokens","system","messages"]

即 temperature / top_p / top_k / thinking 从未被转发。
GLM-5.3 默认开启扩展思考（Anthropic 协议的 thinking 块），
ZCode 原生带思考跑 —— 这正是它显得聪明的主要来源。
桥不转发 => DSH 侧全程无思考链。

改：
- zcodeBridgeServer.ts 新增 passthroughSampling()，透传
  temperature / top_p / top_k / metadata（范围校验，不做默认值）
- thinking 字段原样透传（仅调用方显式传时；不擅自开启，因为
  思考会显著拉长 ttft）
- adapter.ts 从 GenerateOptions 读 temperature / topP / thinking

## ② 并发限流（429 的真语义）

抓到完整拒绝体：

    HTTP 429 {"code":3009,"msg":"model concurrency limit exceeded"}
    HTTP 429 {"code":1005,"msg":"exceed quota limit"}

而 token 额度还剩 299.4 万 => 是并发配额，不是 token 配额。
日志统计吻合：155 次 fast path，143 次 200、仅 1 次 429
=> 并发撞车触发，非稳定拒绝。

改（zcodeBridgeServer.ts）：
- 新增全局串行闸门 runSerialized()，只包 fetch 上游
  ⚠ mint 必须留在闸门外 —— 第一版把 mint 也串行化，
    实测 mintMs 从 200-500ms 暴涨到 2500-3100ms
    （mint 走壳内 renderer RPC，本身 200-800ms，排队后累加）
- 新增 429/502/503 退避重试（仅 1 次；3012 明确不重试，
  因为它有账号冷却惩罚）
- 重试前重新 mint —— captcha 一次性，复用必然失败
  （实测：复用旧头的两次重试全部失败）

可用 ZCODE_BRIDGE_SERIALIZE=0 关闭串行。

实测（并发 6 连）：
  修复前：3/6 成功，3 个 400
  修复后：6/6 全部 200，零失败
  稳态单请求：中位 1932ms（1.3-2.1s）
  mintMs：281-685ms（已从 3000ms 回落）

## ③ 找回被连带砍掉的「能力准则」

上一轮的 system 瘦身砍掉 5244 字符 dynamic 段，但那段其实含两类内容：

  流程指令（有害）："先声明再动手" / "边做边汇报" / "Lead with the outcome"
                    / "You are operating autonomously"
    => 与 DSH 规范冲突，且放在 system 开头压过 DSH 的 prompt

  能力准则（有益）："有足够信息就行动" / "不要重开已做的决定"
                    / "权衡时给推荐而非罗列选项"
    => 正是「ZCode 里聪明」的来源，被连带砍掉了

症状：不啰嗦了，但也不那么果断了 —— 优化了表象，损伤了内核。

改（zcode-official-identity.ts）：新增第三块 "Working style"，
只保留能力准则，逐条剔除流程指令。约 700 字符
（相对原 5244 字符削减 87%）。

不改变 3012 准入性：准入只要求身份块存在（cliPrefix + stable 已是 200），
追加块属于「调用方内容」那一类。
