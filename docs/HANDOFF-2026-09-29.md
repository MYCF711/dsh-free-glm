## 一、这是什么

**`dsh-free-glm`** —— 一个 DSH（DeepSeek Harness）插件，把**本机 ZCode 客户端的免费额度通道**接进 DSH：

- 在 DSH 的「设置 → 模型」里显示为 provider `zcode-bridge`
- 模型：`GLM-5.3`、`GLM-5.3-Flash`
- 请求经本机 ZCode 实例的桥（`http://127.0.0.1:<port>`）转发

**发布仓库**：`https://gitee.com/MYCF711/dsh-free-glm`（tags `v0.10.0` ~ `v0.10.4`）

## 四、已知问题（**不要重复我走过的路**）

### ⚠️ 问题 1：`contextWindow: 200_000` 报小了（**已确证，未修**）

**位置**：`src/product.ts:110-111`

```ts
export const models = [
  { id: "GLM-5.3",       contextWindow: 200_000, maxTokens: 32_768 },
  { id: "GLM-5.3-Flash", contextWindow: 200_000, maxTokens: 32_768 },
]
```

**确证过程**（三条独立证据）：

1. **参数确实生效**（不是回退默认）：
   ```
   源码声明:  200_000
   产物 lib:  200_000
   会话记录:  200000      ← 三者一致
   ```
2. **服务端上限远大于 200K**：向桥发 1500K~6000K 字符（≈375K~1.5M tokens）
   **全部返回 HTTP 200**（未被拒）
3. **对照**：官方 `dpsk`（deepseek-v4.1-flash）报的是 `1_000_000`

**影响**：DSH 的上下文压缩按 `contextWindow` 触发
（`dsh-agent-loop:1250` 把它写进每次请求的上下文）⇒
**报小了会提前压缩 = 额外一次 LLM 调用 = 慢 + 丢上下文**。

**⚠️ 未做**：没有确定「GLM-5.3-Flash 的真实窗口是多少」。
我用了「发超长输入探边界」的方法，但**没探到边界**（6000K 字符仍 200）。
**建议**：先查官方文档（z.ai / bigmodel.cn），别再用探边界的方式（消耗额度）。

### ⚠️ 问题 2：`usage` 恒为全 0（**桥侧，不是我们的**）

```
非流式:  usage: {"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}
流式末帧: "usage":{"prompt_tokens":0,"completion_tokens":0,"total_tokens":0}
```

**影响评估（已做）**：DSH 对 `usage` 的依赖很浅（全仓库只一处注释提及）
⇒ **不是「慢」的原因**，主要影响计费显示。

### ⚠️ 问题 3：「慢」的完整归因**未完成**（**主动暂停**）

**用户观察**：「上面的（deepseek）后发先至，下面的（GLM）很慢」

**已排除**：
- 思考档位：实测 `low`/`high`/`max` = 14.4s / 6.6s / 9.8s（**差异不大**，low 反而最慢）
- `usage` 全 0：见上

**未定位**：单次 HTTP 6.6s，而 DSH 一步 11s —— **中间 4.4s 在哪？**

**⚠️ 有一个未验证的怀疑**（用户提出，值得优先查）：
> 「你确定不是你的参数失效了，直接给你按默认上下文参数处理？」

**已验证的部分**：`contextWindow` 确实是我们报的值（见问题 1 证据 1）。
**未验证的部分**：`maxTokens` / `reasoningEffort` / 其它参数**是否真的透传到桥**。
建议做法：在 `adapter.ts` 组包处**打点记录最终 body**，对比桥收到的（桥有请求日志）。

## 六、踩过的坑（**避免重复**）

### 1. 凭据有两种字段命名（最隐蔽）

```
persistCurrent() 写的:  bridge_token / bridge_port / account_label
池化写的:               bridgePort / bridgeToken / jwt / label

⇒ 读凭据的地方【必须】用 readPoolCredential 归一
⇒ 否则「UI 加入的账号读不到实例地址」→ 多实例分发静默失效
```

**这个模式我连踩三次**（A1 刷新按钮 / D2 适配器 refresh / persistCurrent），
每次都是「构造全新对象、抹掉池化字段」。**改任何写凭据的代码前，先 grep
`credentials.set` 逐个确认是「读-改-写」还是「重建」。**

### 2. `EMPTY_RESPONSE` 在 DSH 的可重试集合里

```
dsh-llm/lib/index.js:216-222
DEFAULT_RETRYABLE_CODES = [EMPTY_RESPONSE_CODE, "RATE_LIMIT", "SERVER", "TIMEOUT", "TRANSPORT"]
```

⇒ 额度耗尽（HTTP 200 + 空内容）会被当**偶发空响应**退避重试 5 次（~15.5s）后失败，
**全程不切号**。判据要认 `failure.code === 'EMPTY_RESPONSE'`。

### 3. 桥的 `/v1/models` 是静态白名单

```
{"id":"GLM-5.3","owned_by":"zcode-free-quota"}
```
**不含账号权益**。权益要从 `/diagnostics/billing` 的
`plans[].entitlements[].capabilities` 读（形如 `["model:glm-5.3-flash"]`）。

### 4. `injected-jwt.txt` 对实例是**必需**的

```
D:\zcode-glm5.3f\_oss_data\.zcode\v2\injected-jwt.txt

⚠ 我把它当脏数据删了（内容是 'h.p.s'），结果实例所有需上游的端点 401
⇒ 恢复方式：桥的 POST /oauth/cli-login（会开浏览器）
⇒ 或 POST /oauth/use-token { token }（运行时注入，不用重启）
```

**它只在模块加载时读一次**（`zcodeBridgeServer.ts:953`），
运行时写文件**不生效**，要用 `/oauth/use-token`。

### 5. 多实例的启动参数（三个，缺一不可）

```
ZCODE_DISABLE_FIXED_REMOTE_DEBUGGING_PORT=1   # main/index.ts:260 硬编码 9229
ZCODE_DESKTOP_USER_DATA_DIR=<独立目录>         # index.ts:368 setPath 覆盖 --user-data-dir
ZCODE_DESKTOP_APPLICATION_NAME=<唯一名>        # desktopRuntimeEnv.ts:61 参与锁判定
```

启动脚本：`D:\zcode-glm5.3f\scripts\start-pool-instance.ps1`
