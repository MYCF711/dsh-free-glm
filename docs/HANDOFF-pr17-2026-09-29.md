## 1. 你的四个阻塞缺口 —— 逐条落实情况

### ① `ctx.zcodeAuth` 从未注册 ✅ 已修

你的探针证据（`ctx.zcodeAuth = undefined`，对照 `raccoonAuth`/`loomyAuth` 都 defined）完全成立。

**根因**：`ZcodeAuth` 是裸 class，没继承 `Service`；而 `ctx.xxxAuth` 的注册**不是**
`index.ts` 显式调用的，是 `Service` 基类构造函数内部 `ctx.provide(name, this)` 做的。
其余九个 auth 全部 `extends Service`，只有 zcode 漏了 —— 所以 PR 注释里写的
「服务名注册为 `ctx.zcodeAuth`」与实现直接矛盾。

**修法**：

```ts
export class ZcodeAuth extends Service {
  constructor(ctx: Context, options: ZcodeAuthOptions = {}) {
    const product = options.product ?? ZCODE
    // ⚠ 必须在 `this.xxx` 赋值之前调 super（JS 语义）
    super(ctx, options.serviceName ?? `${product.id}Auth`)
    ...
  }
}
```

同时 `ZcodeAuthOptions` 加了 `serviceName`（单测需要构造多个实例，而 `Service` 拒绝重复注册）。

> **给你的提示**：`import { Service } from '@deepseek-ai/cordis'` 必须是**值导入**，
> 不能是 `import type` —— 后者编译期被完全擦除，运行时拿不到构造函数。

### ② `registerJetHubRpc` 里 zcode 形参零引用 ✅ 已修

补了两处分支：

**`account.create`**：

```ts
} else if (provider === ZCODE.id) {
  const probe = await zcode.probe()
  if (!probe.available) { return { ok: false, error: {...} } }
  const persisted = await zcode.persistCurrent(refName)
  await pool.addAccount({ id, provider: ZCODE.id, ... })
  return { ok: true, value: { accountId: id, loginUrl: undefined } }

```

⚠ 这里与其余 provider 的**根本差异**：ZCode 没有可换取的 token，
凭据语义是「本机实例的桥是否活着」。所以 `loginUrl` 显式给 `undefined`
（`zcode.startLogin()` 本来就这么定义），前端据此显示「该 provider 无需登录」。

**`account.refresh`**：此前落到 `default` 抛 `Unknown provider: zcode`。
补了 `ZcodeAuth.refreshAccountCredential(refName, pool?, accountId?)` ——
参数顺序与 raccoon 等同款。语义也与其他 provider 不同：

```
其余 provider：拿 refresh_token 换新 token
ZCode：        把发现文件里当前的端口/token 重新落盘到该账号的 ref，并回写昵称
```

因为**没有远端 refresh 端点**。但它不是空操作——实例重启会换端口，
凭据 ref 指向死端口时请求全失败，而 `providerCatalogVisible()` 的判据是
「凭据能否解析」，端口失效会让**整个 zcode 分组从模型选择器里消失**。

## 3. 新增：账号池化（用户需求，超出 PR 原范围）

用户原话：

> 「要做成号池的形态，一般都要 8 个账号起步的，不然用一会就没 token」
> 「要让会话保持，避免请求发到新账号重新吃首轮 tok。要让多会话均分账号，
>   防止会话集中在同账号下并发。只有在账号全部占用时才妥协，不过依旧是会话均摊账号。
>   避免出现单账号超高迸发，而别的账号空闲。」

### 3.1 新增文件

| 文件 | 作用 |
|---|---|
| `src/zcode-pool.ts` | 账号池（增删查 + 额度快照 + 选号）。容量 = **实际登录账号数**，不预设上限 |
| `src/zcode-rotator.ts` | 额度自动接续（主动巡检 60s 节流 + 被动兜底「已失败立即切」） |
| `src/zcode-lease.ts` | **会话租赁调度器**（粘性 + 最少占用均摊） |

### 3.2 调度器的关键设计（有一条值得你看）

**刻意不做「已占用就跳过」的过滤。** 直觉写法是「找一个没人用的账号，没有就随便挑一个」
——那正是用户点名的「单账号超高迸发，而别的账号空闲」的来源。
本模块**从头到尾只有一个选号函数**（最少占用），全占用场景不是特殊分支，
而是同一函数在「最小占用 > 0」时的自然结果 ⇒ 2 账号 4 会话恒为 `2/2`。

平局取候选靠前且**不排序**（用严格 `<`），使「账号顺序 = 用户拖拽优先级」是
**结构性**保证，不依赖 `Array.prototype.sort` 的稳定性。

### 3.3 会话标识：直接用 `options.sessionId`，不要 hash

这一点我原本打算自己造，查证后改成了直接用：

```
dsh-llm/lib/types/types.d.ts:409   sessionId?: Branded<'SessionId'>
dsh-agent-loop/lib/index.js:1259   sessionId: this.session.id
dsh-agent-loop/lib/invariant.js:18 强制校验「a loop-built request must carry a session id」
```

**有不变式强制非空 + 必须是活会话，所以拿不到 `undefined`。**

⚠ 不要 hash system prompt —— 同会话的 `title`/`compaction` 旁路调用 system 不同，
会被算成不同键；hash 前 N 条消息会随步数漂移。

## 4. ⚠ 架构级发现：桥的账号注入是进程级单值

**这是整份文档最需要你注意的一条。**

```ts
// zcodeBridgeServer.ts:953
let injectedJwt: string | undefined = loadInjectedJwtFromDisk()

// 三处消费点，全是 `injectedJwt ?? material.apiKey`：
:2721   authorization: `Bearer ${injectedJwt ?? material.apiKey}`
:3275   const effectiveApiKey = injectedJwt ?? material.apiKey
:3827   const refreshedKey  = injectedJwt ?? refreshed.apiKey
```

我逐项排除过「每请求覆盖」的可能性：

- ✗ 请求体没有 `apiKey` / `token` / `credential` 覆盖字段
- ✗ 没有每请求覆盖的 header 途径
- ⇒ **同一时刻桥只能服务一个账号**

**含义**：单实例下「多会话同时用不同账号」**物理上不可能**。
适配器侧能做到的是「接下来把 `injectedJwt` 设成谁」这个决策按会话归属来算，
但同一时刻仍只有一个生效。

**这是我目前实现的准确语义，别把它误当成「已按会话隔离」。**

### 附带的好消息：切号无副作用

`/v1/chat/completions` 走 fast path，`runConversation()` **每次 createTask() 建独立 task**
（`sseOpen`/`pushedChars`/`chatId` 都是请求内局部变量，无跨请求共享可变状态），
每次现 mint 材料（实测一次性不可复用）。所以**不存在「旧 task 带着旧账号鉴权」的问题**。

⚠ 有个容易踩的坑：`mintAuthMaterial` 的 `sessionId` 参数是**诊断端点专用**
（`directSessionId` 定义在诊断 try 块内），主路径不传。别把诊断路径的机制
误当成主路径的会话链路。

## 5. 多实例化：已跑通，附完整启动参数

要让「多会话用不同账号」真正成立，唯一出路是**每账号一个桥实例**。

### 5.1 三个必须同时设的环境变量（缺一不可）

| 变量 | 为什么需要 | 不设的症状 |
|---|---|---|
| `ZCODE_DISABLE_FIXED_REMOTE_DEBUGGING_PORT=1` | `main/index.ts:260` 硬编码 `appendSwitch("remote-debugging-port", "9229")`，**会覆盖命令行参数** | `bind() returned an error: 通常每个套接字地址只允许使用一次 (0x2740)` + `Cannot start http server for devtools` |
| `ZCODE_DESKTOP_USER_DATA_DIR=<独立目录>` | `index.ts:368` 的 `app.setPath("userData", ...)` **会覆盖命令行 `--user-data-dir`** | 单实例锁互斥，静默退出 |
| `ZCODE_DESKTOP_APPLICATION_NAME=<唯一名>` | `desktopRuntimeEnv.ts:61` 决定 `appData` 下的目录名，参与锁判定 | 锁互斥 |

**这三个不是我们发明的** —— 是官方为 e2e 隔离身份留的。`desktopRuntimeEnv.ts:58-63`
的注释说的就是同一件事：

> e2e 运行的是生产构建，默认会和本机正式版 ZCode 共用 app name / userData，
> **触发 Electron 单实例锁后只激活已有窗口**。这里允许测试**显式隔离运行时身份**。

### 5.2 症状判据（我们踩了两轮才分清）

「第二个实例静默退出」**有两个不同成因**，症状几乎一样（退出码 0、日志只有 3 行）：

| 成因 | 判据 |
|---|---|
| devtools 端口冲突 | stderr 有 `bind() returned an error` |
| 单实例锁 | stderr 干净，只有 3 行正常启动日志 |

**只看「3 行日志」会误判** —— 一定要看 stderr。

// 新增钩子

## 10. 我自己实测确认、但 PR 里没写的两条「别重走」

1. **`@deepseek-ai/dsh-brand` 给 `sessionId` 加类型** → 该包**不在**插件 `node_modules` 里

   已改成恒 `0`，理由写进了注释（占用数语义上就没有「未知」这一档）。
