## 一、背景

本机 captcha 从「无感验证」降级为「**滑块验证**」后，
桥的所有请求返回空回复（`total_tokens: 0`），

## 二、已确认的事实（全部实测，可复用）

### 2.1 环境

| 项 | 值 |
|---|---|
| 目标 | ZCode renderer，CDP `http://127.0.0.1:9229` |
| 弹窗 | `#aliyunCaptcha-window-popup` |
| 背景图 | `#aliyunCaptcha-img`（`img.puzzle`，296×200） |
| 拼图块 | `#aliyunCaptcha-puzzle`（52×200，内容占上方 49×50） |
| 滑块 | `#aliyunCaptcha-sliding-slider`（40×40） |
| 滑轨 | `#aliyunCaptcha-sliding-body`（300×40） |
| prefix | `no8xfe`（与 `AliyunCaptchaConfig` 一致） |

### 2.2 事件注入是**有效的**

CDP `Input.dispatchMouseEvent` 能让滑块真实跟随：

```
拖动 100px → #slider cssLeft: 0px → 100px
拖动  50px → cssLeft: 50px
```

**位移 1:1**，且拖回起点后 `cssLeft` 干净复位（`0px`）。
⇒ 「按下 → 移动 → 移回 → 松开」**不产生提交**，可以安全探测。

### 2.3 拼图块跟随是**非线性的**（关键发现）

密集采样（每 70ms 一次，一次按下期间）：

| 滑块位移 | 拼图块位移 | 比值 |
|---|---|---|
| 10 | 1.12 | 0.11 |
| 50 | 12.72 | 0.25 |
| 100 | 43.20 | 0.43 |
| 150 | 91.42 | 0.61 |
| 200 | 157.40 | 0.79 |

**比值单调递增、趋近 1** —— 不是线性缩放。

⚠ 而且**不是动画延迟**：按住 900ms 后再读，数值与 70ms 时**完全一致**
（43.19 / 157.40）。⇒ 这是 SDK 真实的应用层映射。

### 2.4 缺口定位：颜色判据有效

三种方法对比：

| 方法 | 结果 | 评价 |
|---|---|---|
| 列差分能量 | x=227 | 碰巧接近，依据弱 |
| 列方差 | x=282 | **错**（选中平坦天空） |
| **颜色（低饱和+中高亮度）** | **x=235** | ✅ 有效 |

颜色判据的输出：
```
灰白像素占比最高的列: x=230..233（67%）
连续灰白带:          x=203..256（宽 53，与拼图块 52px 吻合）
```

⚠ 模板匹配（NCC）**不可靠**：top 候选挤在 0.78-0.79，无明确优胜者。
原因是拼图块含半透明叠加，与背景并非精确子图关系。

## 三、做了什么（三次提交）

| # | 方法 | 拖动 | 结果 |
|---|---|---|---|
| 1 | 列差分 + 几何推算 | 204px | ✗ 拒绝 |
| 2 | 颜色判据 + 拟合滞后 | 266px | ✗ 拒绝 |
| 3 | 查表反插值 + **闭环割线迭代** | 234px | ✗ 拒绝 |

第 3 次值得单独说 —— 它**收敛得非常好**：

```
轮1: 拼图块中心 476.0  差 212.2
轮2: 拼图块中心 736.0  差 -47.8
轮4: 拼图块中心 628.9  差  59.3
轮6: 拼图块中心 678.1  差  10.1
轮7: 拼图块中心 688.4  差  -0.2  ← ✓ 到位
```

**拼图块中心与缺口中心只差 0.2 像素**（用实测位置做反馈，不依赖任何外推）。
而且两条独立路径给出一致的拖动量：查表 237.5px、闭环实拖 234.2px。

**⇒ 位置一定是对齐的，但上游仍判失败。**

## 四、结论：卡在**行为特征**，不是几何

对齐到 0.2px 仍被拒，只剩一个解释：

> SDK / 服务端校验的不只是「最终位置」，还有**拖动过程的行为特征**。

CDP 注入的鼠标事件虽然能让 DOM 跟随，但：

- 事件是 **`isTrusted: false`**（CDP 注入的合成事件）
- 轨迹的**时间熵**不如真人（我的间隔是伪随机，真人有微妙的非均匀性）
- 缺少真实的 pointer/touch 事件序列、缺少硬件级输入特征

这与研究文档的结论一致（`aliyun-captcha-research.md` 第 228 行）：

> **`isTrusted` 是所有纯协议方案必须 patch 的第一道关**

真实浏览器里用**真人一次拖动**可以过（研究文档第 227 行：
「真实浏览器 + 真实拖拽事件是公认可行路径」）。

## 六、`isTrusted` 路线：已实测排除

研究文档（`aliyun-captcha-research.md` 第 228 行）称：

> **`isTrusted` 是所有纯协议方案必须 patch 的第一道关**

**本机实测对该结论的适用性做了否证：**

### 6.1 patch 本身打不上

| 尝试 | 结果 |
|---|---|
| `defineProperty(Event.prototype, 'isTrusted', {get})` | 不抛错，但读出来仍 `false` |
| 严格模式重试 | 仍 `false` |
| 在**实例**上 `defineProperty` | 抛 `Cannot redefine property: isTrusted` |

prototype 上的属性描述符是 `{ hasGet: true, configurable: true }` ——
看起来可配置，但 `defineProperty` 静默无效（Chromium 的 native getter 优先）。

### 6.2 更关键：SDK **根本没读它**

用 getter hook 计数，然后发一次真实拖动：

```
isTrusted 被读次数: 0
```

⇒ **SDK 的事件处理器里没有读 `isTrusted`。**

这条否证比「patch 打不上」更有力 —— 即使patch 成功也不会有任何作用。
上游判定的依据在**别处**（很可能是服务端对轨迹/时机的统计判定，
而不是客户端能看到的任何 DOM 信号）。

## 七、最终结论

**程序化完成滑块验证，在当前链路上不可行。**

三层证据：

1. 几何已对齐到 **0.2px**（闭环迭代，用实测位置做反馈，无外推）
2. 两条独立路径给出**一致的拖动量**（查表 237.5px / 闭环 234.2px）
3. 客户端能看到的判据（`isTrusted`）**根本没被读** ——
   说明判定发生在服务端，依据的是行为特征而非 DOM 状态

⇒ **需要真人拖一次。** 这不是代码问题，也没有我能绕过的客户端信号。
