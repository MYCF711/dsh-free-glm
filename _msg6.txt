feat: captcha 降级检测 + 自动退避 —— 防止把设备信誉打坏

## 问题（实测血泪）

上游 captcha 有**信誉**概念。信誉不足时从「无感验证（静默通过）」
降级为「滑块验证（需人工）」。而一旦降级，**继续请求不会让它恢复，
反而让它更糟**。

单日日志分布极其典型：

```
00 时:  96 次 mint 超时    ← 密集调试，越撞越糟
01-05 时: 各 5-7 次        ← 空闲后的自然重试
```

00 时那 96 次**没有任何一次成功收尾** —— 纯损耗。
更糟的是：每次失败都白等满 20 秒超时，用户侧每个请求白等 20 秒
（DSH 多步循环会累加）。

## 机制

把 mint 失败当成**连续信号**而非独立事件：

| 连续失败 | 行为 |
|---|---|
| 1-2 次 | 正常重试（瞬时抖动，自己会好） |
| ≥3 次 | 进入退避：1 → 2 → 4 → 8 → 16 → 30 分钟（封顶） |
| 一次成功 | **立即清零**，退出退避 |

退避期间请求**快速返回**，不再阻塞 20 秒。

## 三个设计决定

### 1. 返回 503 而不是 502

语义不同：
- `502` = 上游/凭据出了问题
- `503` = **暂时**不可用，稍后重试（带 `Retry-After`）

调用方据此区分「该重试」与「该报错」。

### 2. 错误信息明确说清原因

```
ZCode 侧 captcha 处于降级冷却中（连续 N 次失败），约 M 秒后可重试。
这通常意味着设备信誉不足、上游把无感验证降级为滑块 ——
请在 ZCode 窗口里手动完成一次验证。
```

不写这段的话，用户只会看到「mint 失败」，完全不知道该怎么办。

### 3. 只有主链路计入失败

诊断端点（`/diagnostics/*`）的失败**不计入** —— 那是人工探测，
不代表真实流量。混进来会让退避被误触发。

## 验证

### 逻辑单测（参数从源码抽取，防两边漂移）

```
BACKOFF_BASE_MS   = 60000      ← 从源码正则抽取
BACKOFF_THRESHOLD = 3
BACKOFF_MAX_MS    = 1800000    (30 分钟)

第1-2次  →  不冷却
第3次    →  1 分钟
第4次    →  2 分钟
第5次    →  4 分钟
第8次起  →  30 分钟（封顶）
成功一次 →  立即清零

✓ 阈值前不冷却   ✓ 第 3 次触发   ✓ 逐次翻倍   ✓ 封顶 30 分钟
```

### 端到端（对真桥）

```
基线请求: HTTP 200, 12.9s, ok        ← 正常链路不受影响
backoff.entered: 0                   ← captcha 健康时不误触发
回复内容: 「通过」                     ← 有真实输出
```

## 测试自身的一个 bug（记录下来）

第一版参数解析写成：

```js
Number(grab(...)[0].replace(/_/g, ''))
```

那个 `[0]` 是**对字符串取第 0 个字符** —— `"60_000"` 被解析成 `"6"`，
于是 BASE 变成 **6 毫秒**。

症状隐蔽：断言「阈值前不冷却」仍通过（与 BASE 无关），
只有「封顶 30 分钟」挂了 —— 而挂的原因是**测试自己的解析**。

⚠ 若不追下去，很容易**误改实现去迁就错误的测试**。
现在改成先剥下划线再转数字，并处理 `30 * 60000` 这类表达式。

## 可关

`ZCODE_BRIDGE_BACKOFF=0` 关闭（诊断用）。
